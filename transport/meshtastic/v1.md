# Meshtastic Transport

> Status: Draft  
> Version: 1

## 1. Scope

This document defines a Meshtastic transport for delivering an existing serialized `SignedEnvelope` over a Meshtastic mesh.

Meshtastic is only a transport layer. It MUST NOT change the canonical payload, signature semantics, sensor identity, authorization model, or deduplication rules of the Connectivity Protocol.

The transport MUST preserve the exact serialized bytes of `SignedEnvelope` end-to-end.

```text
sensor
  |
  | create + sign
  v
SignedEnvelope
  |
  | exact serialized protobuf bytes
  v
Meshtastic framing
  |
  | reliable unicast
  v
configured gateway
  |
  | reassembly
  v
exact original SignedEnvelope bytes
  |
  v
existing ingress pipeline
  |
  +--> signature verification
  +--> authorization
  +--> content-based deduplication
  +--> GossipSub / upstream delivery
```

## 2. Design goals

The transport is designed around the following principles:

1. Preserve the original serialized `SignedEnvelope` byte-for-byte.
2. Reuse the existing edge verification, authorization, and deduplication pipeline.
3. Keep the Meshtastic ingress adapter transport-specific and otherwise minimal.
4. Use reliable unicast delivery to a configured gateway.
5. Avoid adding a second retry protocol on top of Meshtastic firmware retries.
6. Support fragmentation only when a serialized envelope does not fit in one Meshtastic application payload.
7. Bound all receiver-side memory and reassembly state.
8. Keep transport identity separate from signed sensor identity.

## 3. Meshtastic application port

During development, implementations SHOULD use:

```text
PortNum::PRIVATE_APP = 256
```

A production deployment SHOULD obtain a registered third-party Meshtastic `PortNum`.

The Meshtastic built-in telemetry application port MUST NOT be used for Connectivity Protocol envelopes.

Using the built-in telemetry application would require translating the sensor payload into Meshtastic telemetry messages and would break end-to-end preservation of the original signed envelope.

The application port identifies the Connectivity Protocol transport payload.

## 4. Delivery model

Transport v1 is unicast-only.

Each sensor is configured with the Meshtastic node identifier of an ingress gateway.

Every transport packet MUST be sent to that gateway as unicast.

Recommended delivery parameters:

```text
destination = configured gateway node
want_ack    = true
```

Meshtastic firmware is responsible for routing acknowledgements and packet retries.

Host-side code MUST NOT run an independent timer-based retry loop in parallel with Meshtastic firmware retries.

The host submits a fragment once and observes the final Meshtastic delivery result.

If Meshtastic reports terminal delivery failure, higher-level application policy MAY decide to retry the envelope later.

Alternative gateway selection, broadcast delivery, and gateway discovery are outside the scope of transport v1.

## 5. Payload size and fragmentation

A Meshtastic application payload can carry up to 233 bytes.

This transport uses a fixed 9-byte fragment header.

Therefore the protocol maximum fragment body is:

```text
233 - 9 = 224 bytes
```

A sender MAY choose a smaller fragment body size for operational reasons.

A receiver MUST accept fragment bodies from zero up to 224 bytes, subject to the rules below.

Typical sensors SHOULD aim to keep the full serialized `SignedEnvelope` small enough to fit into a single transport frame whenever practical.

Fragmentation is an escape hatch, not the preferred steady-state telemetry path.

## 6. Frame format

Every Connectivity Protocol Meshtastic packet uses the same framing format, including messages that fit into one packet.

```text
Offset  Size  Field
------  ----  -----------------------------
0       2     Magic: ASCII "CP"
2       1     Version
3       4     Message ID
7       1     Fragment index
8       1     Fragment count
9       N     Fragment body
```

Total header size:

```text
9 bytes
```

### 6.1 Magic

The first two bytes MUST be:

```text
0x43 0x50
```

which is ASCII:

```text
CP
```

The magic allows an ingress to cheaply reject unrelated payloads and provides an additional sanity check even when a dedicated Meshtastic `PortNum` is used.

### 6.2 Version

For this specification:

```text
version = 1
```

Packets with unsupported versions MUST be rejected before reassembly.

### 6.3 Message ID

`message_id` is the first 32 bits of:

```text
SHA256(raw_signed_envelope_bytes)
```

The byte order MUST be fixed by implementation and test vectors.

Big-endian interpretation is RECOMMENDED:

```text
message_id = first_u32_be(SHA256(raw_signed_envelope_bytes))
```

The 32-bit value is only a compact reassembly identifier.

It is NOT:

- a cryptographic authenticity token;
- a replacement for the full envelope hash;
- a replacement for the envelope signature;
- globally collision-free.

Security decisions MUST NOT rely on the fragment `message_id`.

### 6.4 Fragment index

`fragment_index` is zero-based.

For a message with `fragment_count = N`, valid indexes are:

```text
0 .. N-1
```

### 6.5 Fragment count

`fragment_count` MUST be greater than zero.

Receivers MUST reject frames whose declared fragment count exceeds the configured implementation limit.

## 7. Fragmentation algorithm

Given the exact serialized `SignedEnvelope` bytes:

```text
raw_envelope
```

the sender computes:

```text
message_id = first_u32_be(SHA256(raw_envelope))
```

The sender splits `raw_envelope` into sequential chunks of at most 224 bytes.

For each chunk:

```text
frame.magic          = "CP"
frame.version        = 1
frame.message_id     = message_id
frame.fragment_index = index
frame.fragment_count = total_count
frame.body           = chunk
```

A one-fragment message still uses the full transport header:

```text
fragment_index = 0
fragment_count = 1
```

There is no separate unfragmented wire format.

## 8. Reassembly key

Receiver reassembly state MUST NOT be keyed by `message_id` alone.

At minimum, the key MUST include the Meshtastic sender:

```text
(mesh_sender, message_id)
```

For example:

```text
ReassemblyKey {
    from:       MeshPacket.from,
    message_id: frame.message_id,
}
```

This prevents unrelated senders that happen to use the same 32-bit message identifier from sharing the same reassembly state.

The Meshtastic sender identity is transport metadata only.

It MUST NOT replace the signed sensor identity contained in the Connectivity Protocol envelope and MUST NOT be used as the authoritative authorization identity.

## 9. Reassembly rules

The receiver SHOULD validate each frame before storing fragment state.

At minimum it MUST validate:

1. the expected Meshtastic application `PortNum`;
2. magic bytes;
3. protocol version;
4. non-zero fragment count;
5. fragment index is less than fragment count;
6. fragment count is within configured limits;
7. fragment body length is at most 224 bytes;
8. total reassembled size cannot exceed the configured maximum.

For the first fragment received for a reassembly key, the receiver records the declared fragment count.

Subsequent fragments for that key MUST declare the same fragment count.

A mismatch MUST invalidate or poison that reassembly state.

Fragments MAY arrive out of order.

Reassembly completes only when all fragment indexes are present.

The final envelope bytes are reconstructed by concatenating fragment bodies in ascending `fragment_index` order.

## 10. Duplicate fragments

If the receiver gets the same:

```text
(mesh_sender, message_id, fragment_index)
```

more than once:

- if the fragment body is byte-identical, the duplicate SHOULD be ignored;
- if the fragment body differs, the receiver MUST treat it as a fragment conflict.

A receiver SHOULD increment a conflict metric and discard or poison the affected reassembly state.

Fragment headers and fragment IDs are not authenticated.

Final authenticity is established only by the normal Connectivity Protocol signature verification step after reassembly.

## 11. Reassembly limits

An implementation MUST bound resource usage.

Recommended defaults:

```text
max_reassembled_bytes = 4096
max_fragments         = 32
max_pending           = 128
reassembly_timeout    = 60 seconds
```

These are operational defaults, not immutable protocol constants.

Receivers SHOULD expose them as configuration.

Expired partial messages MUST be discarded.

When the pending reassembly limit is reached, implementations SHOULD reject new assemblies rather than allowing unbounded memory growth.

## 12. Exact-byte preservation

After reassembly, the resulting byte sequence MUST be the exact original serialized `SignedEnvelope`.

Ingress code MUST preserve these bytes.

It MUST NOT:

1. decode the protobuf;
2. re-encode it;
3. use the re-encoded result as the canonical envelope bytes.

The original reassembled bytes are the authoritative transport payload.

A structural decode MAY be performed to construct the in-memory envelope object, but downstream deduplication, content hashing, and republishing SHOULD continue to use the original byte sequence.

## 13. Ingress boundary

The Meshtastic ingress SHOULD behave as a transport adapter.

Its responsibility is:

```text
receive Meshtastic packet
        |
        v
filter PortNum
        |
        v
parse CP frame
        |
        v
bounded reassembly
        |
        v
structural SignedEnvelope decode
        |
        v
IngressMessage
```

The ingress SHOULD NOT duplicate canonical Connectivity Protocol logic.

In particular, it SHOULD NOT independently implement:

- signature policy;
- authorization policy;
- global content deduplication;
- GossipSub publication policy.

Those operations belong in the existing common edge pipeline.

Conceptually:

```text
IngressMessage {
    envelope,
    raw_envelope,
    transport = Meshtastic,
    transport_metadata = {
        mesh_sender,
    },
    received_at,
}
```

## 14. ACK semantics

Meshtastic packet acknowledgement and Connectivity Protocol acceptance are different events.

They MUST NOT be presented as equivalent.

The following states are distinct:

```text
Meshtastic ACK
    the radio packet reached the destination Meshtastic node

reassembly complete
    all fragments were reconstructed

edge accepted
    Connectivity Protocol signature and authorization succeeded

upstream published
    the accepted envelope was published to the next network layer
```

Transport v1 defines no application-level `COMMIT` or `RECEIPT` message.

If a future protocol version needs confirmation that a complete envelope passed the canonical edge pipeline, that acknowledgement MUST be specified separately from normal Meshtastic routing ACKs.

## 15. Retry behaviour

For reliable unicast, retries SHOULD be delegated to Meshtastic firmware.

The host SHOULD submit each fragment once with:

```text
want_ack = true
```

and observe Meshtastic delivery status.

The host MUST NOT immediately retransmit the same fragment based on its own short timeout while Meshtastic may still be performing router-level retries.

After terminal delivery failure, higher-level application policy MAY:

- retry later;
- persist the envelope for later delivery;
- drop the envelope according to local policy.

Such policy is outside this framing specification.

## 16. Gateway identity

The sensor MUST know the destination Meshtastic node identifier of its ingress gateway before sending.

Gateway discovery is not part of transport v1.

Gateway configuration MAY be provisioned:

- at manufacturing time;
- during sensor setup;
- through local configuration;
- through a separate management protocol.

The configured Meshtastic gateway identity is transport configuration only.

It is not part of the signed `SignedEnvelope`.
