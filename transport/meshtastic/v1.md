# Meshtastic Transport

> Status: Draft  
> Version: 1

## 1. Scope

This document defines a Meshtastic transport for delivering an existing serialized `SignedEnvelope` over a Meshtastic mesh.

Meshtastic is a transport layer only. It MUST NOT change the canonical payload, signature semantics, sensor identity, authorization model, or deduplication rules of the Connectivity Protocol.

The transport MUST preserve the exact serialized bytes of `SignedEnvelope` end-to-end.

```text
sensor
  |
  | create + sign
  v
SignedEnvelope
  |
  | exact serialized protobuf bytes
  v
Meshtastic transport framing
  |
  | reliable unicast
  v
configured gateway
  |
  | frame validation / bounded reassembly
  v
exact original SignedEnvelope bytes
  |
  v
existing ingress pipeline
  |
  +--> structural decode
  +--> signature verification
  +--> authorization
  +--> content-based deduplication
  +--> upstream delivery
```

## 2. Normative language

The key words `MUST`, `MUST NOT`, `REQUIRED`, `SHALL`, `SHALL NOT`, `SHOULD`, `SHOULD NOT`, `RECOMMENDED`, `MAY`, and `OPTIONAL` in this document are to be interpreted as normative requirements.

## 3. Design goals

The transport is designed around the following principles:

1. Preserve the original serialized `SignedEnvelope` byte-for-byte.
2. Reuse the existing Connectivity Protocol verification, authorization, and deduplication pipeline.
3. Keep the Meshtastic ingress adapter transport-specific and otherwise minimal.
4. Use reliable unicast delivery to a configured gateway.
5. Avoid a second short-timescale retry protocol on top of Meshtastic firmware retries.
6. Keep the common single-packet path as small as possible.
7. Use fragmentation only when the serialized envelope cannot fit in one Meshtastic application payload.
8. Bound receiver-side memory and reassembly state.
9. Keep Meshtastic transport identity separate from signed sensor identity.
10. Treat transport framing identifiers as routing and reassembly metadata, never as authentication.

## 4. Meshtastic application port

Connectivity Protocol frames MUST use a dedicated Meshtastic application `PortNum`.

During development and controlled deployments, implementations MAY use:

```text
PortNum::PRIVATE_APP = 256
```

Production deployments SHOULD obtain and use a registered third-party Meshtastic `PortNum`.

`TELEMETRY_APP` MUST NOT be used for Connectivity Protocol envelopes. A Connectivity Protocol frame carries opaque serialized `SignedEnvelope` bytes and does not use the Meshtastic `Telemetry` protobuf schema.

The Meshtastic application port identifies the payload as a Connectivity Protocol transport frame. The first byte of the application payload identifies the transport version and frame type.

## 5. Delivery model

This transport is unicast-only.

Each sensor MUST be configured with the Meshtastic node identifier of an ingress gateway before sending Connectivity Protocol traffic.

Each transport packet MUST be sent to the configured gateway as unicast.

Recommended Meshtastic delivery parameters are:

```text
destination = configured gateway node
want_ack    = true
```

Meshtastic firmware is responsible for routing acknowledgements and its normal packet retry behavior.

Host-side code MUST NOT run an independent short-timeout retry loop in parallel with Meshtastic firmware retries.

The sender submits each Meshtastic packet once and observes the final Meshtastic delivery result. After terminal delivery failure, higher-level application policy MAY persist or retry the complete envelope later.

Gateway discovery, gateway election, broadcast delivery, and multi-gateway fan-out are outside the scope of this transport.

## 6. Payload limits

A Meshtastic `Data.payload` can carry at most 233 bytes.

The transport defines two frame types:

```text
SINGLE    1-byte header  + up to 232 bytes of SignedEnvelope
FRAGMENT  8-byte header  + up to 225 bytes of fragment body
```

A serialized `SignedEnvelope` of 232 bytes or less MUST use a `SINGLE` frame.

A serialized `SignedEnvelope` larger than 232 bytes MUST use `FRAGMENT` frames.

Fragmentation is intended as an escape hatch for envelopes that do not fit in one Meshtastic application payload. Implementations SHOULD keep normal telemetry envelopes small enough to use `SINGLE` whenever practical.

## 7. Control byte

Every Connectivity Protocol Meshtastic frame starts with a one-byte control field.

The control byte is encoded as:

```text
  7 6 5 4 3 2 1 0
 +---+-----------+
 | T |  VERSION  |
 +---+-----------+
   2       6
  bits    bits
```

Where:

```text
bits 7..6 = frame type
bits 5..0 = transport version
```

For this specification:

```text
version = 1
```

Frame type values are:

| Type bits | Name | Meaning |
|---|---|---|
| `00` | `SINGLE` | Complete `SignedEnvelope` follows the control byte |
| `01` | `FRAGMENT` | A fragment header and fragment body follow |
| `10` | reserved | Reserved for future protocol use |
| `11` | reserved | Reserved for future protocol use |

Therefore the defined version-1 control values are:

```text
0x01 = SINGLE
0x41 = FRAGMENT
```

A receiver MUST reject unsupported versions and reserved frame types.

A receiver MUST NOT infer framing from the contents of `SignedEnvelope`. Frame identification is performed only by:

```text
Meshtastic PortNum
        +
control byte
```

## 8. SINGLE frame

A complete serialized envelope that fits in one Meshtastic application payload is carried as:

```text
Offset  Size    Field
------  ------  -----------------------------
0       1       Control = 0x01
1       N       Raw SignedEnvelope bytes
```

Where:

```text
1 <= N <= 232
```

The payload is therefore:

```text
+---------+----------------------------------+
|  0x01   | exact SignedEnvelope bytes       |
+---------+----------------------------------+
  1 byte              1..232 bytes
```

The receiver MUST treat every byte after the control byte as the exact serialized `SignedEnvelope`.

The receiver MUST NOT add, remove, normalize, decode/re-encode, or otherwise transform these bytes before passing them to the common ingress pipeline.

A zero-length `SINGLE` body is malformed and MUST be rejected.

## 9. FRAGMENT frame

A fragmented envelope is carried using the following format:

```text
Offset  Size    Field
------  ------  -----------------------------
0       1       Control = 0x41
1       6       Message ID
7       1       Fragment descriptor
8       N       Fragment body
```

Where:

```text
1 <= N <= 225
```

Total fragment header size:

```text
8 bytes
```

Maximum fragment body size:

```text
233 - 8 = 225 bytes
```

### 9.1 Message ID

`message_id` is the first six octets of the SHA-256 digest of the exact serialized envelope:

```text
message_id = SHA256(raw_envelope)[0:6]
```

The six octets are copied directly from the digest in digest order.

`message_id` is a byte string, not an integer. No byte-order conversion is performed.

For example:

```text
SHA256("hello") =
2c f2 4d ba 5f b0 a3 0e ...

message_id =
2c f2 4d ba 5f b0
```

The 48-bit `message_id` is only a compact transport-level reassembly identifier.

It MUST NOT be treated as:

- a cryptographic authenticity token;
- an authorization identity;
- a replacement for the complete envelope hash;
- a replacement for the envelope signature;
- a globally collision-free identifier;
- a Connectivity Protocol deduplication key.

Security decisions MUST NOT rely on `message_id`.

### 9.2 Fragment descriptor

The fragment descriptor packs the total fragment count and the zero-based fragment index into one byte:

```text
  7 6 5 4 3 2 1 0
 +-------+-------+
 | COUNT | INDEX |
 +-------+-------+
    4       4
   bits    bits
```

The high nibble stores:

```text
fragment_count - 1
```

The low nibble stores:

```text
fragment_index
```

Decoding is therefore:

```text
fragment_count = ((descriptor >> 4) & 0x0f) + 1
fragment_index = descriptor & 0x0f
```

For fragmented envelopes:

```text
2 <= fragment_count <= 16
0 <= fragment_index < fragment_count
```

Example: the second fragment of a three-fragment envelope has:

```text
fragment_count = 3
fragment_index = 1

descriptor =
((3 - 1) << 4) | 1
= 0x21
```

A `FRAGMENT` frame declaring `fragment_count = 1` is malformed and MUST be rejected.

## 10. Fragmentation algorithm

Given the exact serialized bytes:

```text
raw_envelope
```

the sender proceeds as follows.

If:

```text
len(raw_envelope) <= 232
```

the sender MUST emit one `SINGLE` frame.

Otherwise the sender MUST:

1. Compute:

   ```text
   message_id = SHA256(raw_envelope)[0:6]
   ```

2. Split `raw_envelope` sequentially into chunks of 225 bytes, except that the final chunk MAY contain fewer bytes.

3. Compute:

   ```text
   fragment_count = ceil(len(raw_envelope) / 225)
   ```

4. Reject the envelope for this transport if:

   ```text
   fragment_count > 16
   ```

5. Emit one `FRAGMENT` frame for each chunk.

For every non-final fragment:

```text
fragment_body_length MUST equal 225
```

For the final fragment:

```text
1 <= fragment_body_length <= 225
```

The maximum serialized envelope that can be represented by this framing is:

```text
16 * 225 = 3600 bytes
```

A sender MUST NOT create a fragmented transport message larger than 3600 bytes.

## 11. Sending fragments

Fragments MAY be delivered by the mesh out of order.

A sender SHOULD submit fragments in ascending `fragment_index` order unless an implementation has a specific reason to do otherwise.

Each fragment is a separate Meshtastic packet and SHOULD use:

```text
want_ack = true
```

The sender MUST NOT interpret successful delivery of one fragment as successful delivery of the complete `SignedEnvelope`.

The complete envelope is transport-deliverable only after every fragment has reached the gateway and reassembly has completed.

## 12. Reassembly key

Receiver reassembly state MUST NOT be keyed by `message_id` alone.

At minimum, the reassembly key MUST include:

```text
ingress_scope
mesh_sender
message_id
```

Conceptually:

```text
ReassemblyKey {
    ingress_scope,
    mesh_sender: MeshPacket.from,
    message_id:  frame.message_id,
}
```

`ingress_scope` is implementation-local metadata that distinguishes independently addressed Meshtastic gateway ingress contexts. For a process connected to one gateway node, the connection or gateway instance identifier is sufficient.

If one process receives traffic for multiple independently addressed local Meshtastic gateway identities, `ingress_scope` MUST distinguish those identities.

`MeshPacket.channel` is not part of the Connectivity Protocol identity model and is not required in the reassembly key.

The Meshtastic sender identifier is transport metadata only. It MUST NOT replace the signed sensor identity contained in the `SignedEnvelope` and MUST NOT be used as the authoritative Connectivity Protocol authorization identity.

## 13. Frame validation

The receiver MUST validate a frame before committing unbounded or attacker-controlled state.

For every received packet, the receiver MUST validate:

1. The expected Meshtastic application `PortNum`.
2. `Data.payload` contains at least one byte.
3. The control-byte version is supported.
4. The control-byte frame type is defined by this specification.
5. The Meshtastic destination is the local configured gateway identity, where that information is available to the ingress implementation.

For a `SINGLE` frame, the receiver MUST additionally validate:

```text
1 <= body_length <= 232
```

For a `FRAGMENT` frame, the receiver MUST additionally validate:

```text
frame_length >= 9
2 <= fragment_count <= 16
fragment_index < fragment_count
1 <= body_length <= 225
```

For every non-final fragment:

```text
body_length == 225
```

For the final fragment:

```text
1 <= body_length <= 225
```

Malformed frames MUST be rejected and MUST NOT be passed to the common Connectivity Protocol ingress pipeline.

## 14. Reassembly rules

For the first accepted fragment associated with a reassembly key, the receiver creates bounded reassembly state and records:

```text
message_id
fragment_count
first_seen
last_progress
received fragment indexes
fragment bodies
```

Subsequent fragments for the same key MUST declare the same `fragment_count`.

A fragment-count mismatch for an existing reassembly key is a conflict. The receiver MUST discard or poison the affected reassembly state.

Fragments MAY arrive out of order.

Reassembly completes only when every fragment index from:

```text
0 .. fragment_count - 1
```

is present.

The receiver reconstructs the serialized envelope by concatenating fragment bodies in ascending `fragment_index` order.

After concatenation, the receiver MUST verify:

```text
SHA256(reassembled_envelope)[0:6] == message_id
```

If the check fails, the reassembled message MUST be discarded.

This digest-prefix check validates transport reassembly consistency only. It does not establish authenticity.

After the digest-prefix check succeeds, the receiver MUST pass the exact reconstructed byte sequence to the normal Connectivity Protocol ingress pipeline.

## 15. Duplicate and conflicting fragments

A receiver may receive the same:

```text
(ingress_scope, mesh_sender, message_id, fragment_index)
```

more than once.

If the repeated fragment body is byte-identical, the receiver SHOULD ignore the duplicate without resetting reassembly state.

Receiving an identical duplicate MUST NOT refresh `last_progress`.

If the repeated fragment body differs, the receiver MUST treat the condition as a fragment conflict and MUST discard or poison the affected reassembly state.

Implementations SHOULD expose a metric for fragment conflicts.

Transport fragment headers and fragment identifiers are not authoritative authentication data. Final authenticity is established only by the normal Connectivity Protocol signature verification performed after the exact envelope bytes have been recovered.

## 16. Resource limits

A receiver MUST place finite limits on reassembly memory and state.

The wire protocol itself imposes:

```text
max_fragment_body     = 225 bytes
max_fragments         = 16
max_reassembled_bytes = 3600 bytes
```

An implementation MUST additionally bound at least:

```text
pending assemblies globally
pending assemblies per mesh sender
buffered bytes globally
buffered bytes per mesh sender
idle lifetime
absolute assembly lifetime
```

Recommended gateway defaults are:

```text
max_pending_global          = 128
max_pending_per_sender      = 8
max_buffered_bytes_global   = 262144
max_buffered_bytes_per_sender = 14400
idle_timeout                = 60 seconds
absolute_timeout            = 300 seconds
```

These operational values MAY be made configurable, but implementations MUST NOT permit unbounded growth.

`idle_timeout` is measured from the most recent newly accepted fragment that advanced an incomplete assembly.

Duplicate fragments MUST NOT extend `idle_timeout`.

`absolute_timeout` is measured from creation of the reassembly state and MUST NOT be extended.

Expired partial assemblies MUST be discarded.

When a configured resource limit is reached, the receiver SHOULD reject creation of new assemblies rather than evicting actively progressing state unpredictably.

## 17. Exact-byte preservation

The authoritative transport payload is the original serialized `SignedEnvelope` byte sequence.

For `SINGLE`, it is:

```text
Data.payload[1:]
```

For `FRAGMENT`, it is the byte sequence produced by ordered concatenation of all validated fragment bodies.

Ingress code MUST preserve these bytes exactly.

Ingress code MUST NOT:

1. decode the protobuf and use a re-encoded serialization as the canonical envelope;
2. reorder protobuf fields;
3. normalize unknown fields;
4. alter the serialized representation before signature verification, hashing, deduplication, or upstream forwarding when those operations are defined over the original serialized bytes.

A structural protobuf decode MAY be performed after a complete envelope has been recovered in order to construct an in-memory `SignedEnvelope` object.

The original raw byte sequence MUST remain available to the common ingress pipeline.

## 18. Ingress boundary

The Meshtastic ingress SHOULD behave as a narrow transport adapter.

Its responsibility is:

```text
receive Meshtastic packet
        |
        v
filter dedicated PortNum
        |
        v
parse control byte
        |
        +---- SINGLE ------+
        |                  |
        |                  v
        |            raw envelope
        |
        +---- FRAGMENT ----+
                           |
                           v
                  bounded reassembly
                           |
                           v
                  message_id check
                           |
                           v
                     raw envelope
                           |
                           v
                structural decode
                           |
                           v
                    IngressMessage
```

The Meshtastic ingress SHOULD NOT independently implement canonical Connectivity Protocol policy.

In particular, common policy SHOULD remain responsible for:

- signature verification;
- sensor authorization;
- canonical content hashing;
- global content deduplication;
- upstream publication policy.

Conceptually:

```text
IngressMessage {
    envelope,
    raw_envelope,
    transport = Meshtastic,
    transport_metadata = {
        mesh_sender,
        ingress_scope,
    },
    received_at,
}
```

Additional Meshtastic diagnostic metadata MAY be attached, but it MUST NOT change the authoritative sensor identity or canonical envelope bytes.

## 19. ACK semantics

Meshtastic routing acknowledgement and Connectivity Protocol acceptance are different events and MUST NOT be presented as equivalent.

The following states are distinct:

```text
Meshtastic ACK
    the individual Meshtastic packet reached the destination node

reassembly complete
    every transport fragment was received and reconstructed

transport validated
    framing and message_id consistency checks succeeded

edge accepted
    Connectivity Protocol signature and authorization succeeded

upstream published
    the accepted envelope was handed to the next network layer
```

A Meshtastic ACK confirms only the Meshtastic packet delivery result represented by that ACK.

It does not prove that:

```text
the complete SignedEnvelope was received
the envelope was structurally valid
the signature was valid
the sensor was authorized
the envelope was accepted
the envelope was published upstream
```

This transport defines no application-level receipt or commit frame.

If an application requires confirmation that a complete envelope passed the canonical edge pipeline, that acknowledgement MUST be specified separately from Meshtastic routing ACKs.

## 20. Retry behavior

For reliable unicast, short-timescale packet retries SHOULD be delegated to Meshtastic firmware.

The host SHOULD submit each `SINGLE` or `FRAGMENT` packet once with:

```text
want_ack = true
```

and observe the Meshtastic delivery result.

The host MUST NOT immediately retransmit the same packet based on its own short timeout while Meshtastic may still be performing routing-level retries.

After terminal Meshtastic delivery failure, higher-level application policy MAY:

- persist the original complete `SignedEnvelope`;
- retry delivery later;
- choose another configured transport;
- drop the envelope according to local policy.

Any later retry MUST be generated from the same original serialized `SignedEnvelope` bytes if end-to-end byte preservation is required.

Long-term persistence and store-and-forward policy are outside the scope of this framing specification.

## 21. Gateway identity

The sensor MUST know the destination Meshtastic node identifier of its ingress gateway before sending.

Gateway identity MAY be provisioned through manufacturing, setup, local configuration, or a separate management protocol.

Gateway discovery is outside the scope of this transport.

The configured Meshtastic gateway identity is transport configuration only. It is not part of the authoritative sensor identity and need not be part of the signed `SignedEnvelope`.

## 22. Meshtastic security

Connectivity Protocol security MUST NOT depend on Meshtastic transport security alone.

Deployments SHOULD use authenticated Meshtastic PKI direct-message encryption when it is available and correctly provisioned.

Regardless of Meshtastic encryption mode, the authoritative end-to-end authenticity decision MUST be made by the normal Connectivity Protocol verification of the recovered `SignedEnvelope`.

In particular:

```text
Meshtastic node identity
        !=
Connectivity Protocol sensor identity
```

and:

```text
Meshtastic packet authentication
        !=
SignedEnvelope authentication
```

An attacker able to inject, alter, replay, or withhold transport frames may cause denial of service or reassembly conflicts. Such transport behavior MUST NOT allow an invalid `SignedEnvelope` to bypass normal signature and authorization checks.

`message_id`, fragment descriptors, Meshtastic sender identifiers, and routing acknowledgements MUST NOT be used as substitutes for signed Connectivity Protocol data.

## 23. Meshtastic routing compatibility

Connectivity Protocol uses a custom Meshtastic application `PortNum`.

Mesh deployments that carry Connectivity Protocol traffic MUST ensure that all required forwarding nodes are configured to rebroadcast that application port.

Nodes configured with Meshtastic rebroadcast policies that forward only core application ports may drop Connectivity Protocol packets.

Deployment operators MUST verify custom-port forwarding along the intended mesh path.

This requirement applies independently of whether the Connectivity Protocol application uses `PRIVATE_APP` during development or a registered third-party `PortNum` in production.

## 24. Frame examples

### 24.1 SINGLE

For a serialized envelope beginning with:

```text
0a 03 66 6f 6f ...
```

the Meshtastic application payload is:

```text
01 0a 03 66 6f 6f ...
^^
control = SINGLE, version = 1
```

The byte `0x0a` is the first byte of the original `SignedEnvelope`.

### 24.2 FRAGMENT

For a fragmented envelope whose message ID is:

```text
2c f2 4d ba 5f b0
```

and for fragment index `1` of `3`, the descriptor is:

```text
0x21
```

The frame begins:

```text
41 2c f2 4d ba 5f b0 21 ...
^^ ^-----------------^ ^^
|          |           |
|          |           +-- fragment 1 of 3
|          +-------------- message_id
+------------------------- FRAGMENT, version 1
```

## 25. Sender algorithm

A sender implementation is equivalent to:

```text
raw = exact serialized SignedEnvelope bytes

if len(raw) == 0:
    reject

if len(raw) <= 232:
    send_meshtastic(
        payload = 0x01 || raw,
        destination = configured_gateway,
        want_ack = true,
    )
    return

if len(raw) > 3600:
    reject for this transport

id = SHA256(raw)[0:6]
chunks = split_sequentially(raw, 225)
count = len(chunks)

for index, chunk in chunks:
    descriptor = ((count - 1) << 4) | index

    send_meshtastic(
        payload =
            0x41
            || id
            || descriptor
            || chunk,
        destination = configured_gateway,
        want_ack = true,
    )
```

This pseudocode describes framing only. Scheduling, queueing, radio duty-cycle policy, persistence, and higher-level retry policy remain implementation concerns.

## 26. Receiver algorithm

A receiver implementation is equivalent to:

```text
on_meshtastic_data(packet):

    if packet.portnum != CONNECTIVITY_PROTOCOL_PORT:
        ignore

    payload = packet.payload

    if len(payload) < 1:
        reject

    control = payload[0]
    version = control & 0x3f
    type    = control >> 6

    if version != 1:
        reject

    if type == SINGLE:
        raw = payload[1:]

        if len(raw) < 1 or len(raw) > 232:
            reject

        submit_raw_envelope(raw, transport_metadata)
        return

    if type != FRAGMENT:
        reject

    if len(payload) < 9:
        reject

    id         = payload[1:7]
    descriptor = payload[7]
    body       = payload[8:]

    count = ((descriptor >> 4) & 0x0f) + 1
    index = descriptor & 0x0f

    if count < 2 or count > 16:
        reject

    if index >= count:
        reject

    if len(body) < 1 or len(body) > 225:
        reject

    if index < count - 1 and len(body) != 225:
        reject

    key = (
        ingress_scope,
        packet.from,
        id,
    )

    bounded_store_fragment(
        key,
        count,
        index,
        body,
    )

    if not all_fragments_present(key):
        return

    raw = concatenate_in_index_order(key)

    if len(raw) > 3600:
        discard(key)
        return

    if SHA256(raw)[0:6] != id:
        discard(key)
        return

    discard_reassembly_state(key)
    submit_raw_envelope(raw, transport_metadata)
```

The receiver MUST apply configured memory, sender, idle-timeout, and absolute-timeout limits around `bounded_store_fragment`.

## 27. Interoperability requirements

A conforming sender MUST:

1. use the dedicated Connectivity Protocol Meshtastic application port;
2. emit only version-1 `SINGLE` or `FRAGMENT` frames defined here;
3. use `SINGLE` for serialized envelopes of 232 bytes or less;
4. use exactly 225 bytes for every non-final fragment body;
5. derive `message_id` as the first six raw SHA-256 digest octets;
6. preserve the exact serialized `SignedEnvelope`;
7. address packets to the configured gateway as unicast.

A conforming receiver MUST:

1. demultiplex by the dedicated Meshtastic application port;
2. parse and validate the control byte before inspecting frame-specific fields;
3. reject unsupported versions and reserved frame types;
4. enforce all frame-size and fragment-count limits;
5. use sender-scoped bounded reassembly state;
6. accept out-of-order fragments;
7. detect duplicate and conflicting fragments;
8. verify the message ID after complete reassembly;
9. preserve the exact reconstructed bytes;
10. pass complete envelopes into the common Connectivity Protocol verification and authorization pipeline;
11. never treat Meshtastic sender identity or transport framing identifiers as authoritative sensor identity.

## 28. Protocol constants

For convenience, the version-1 constants are summarized below:

| Constant | Value |
|---|---:|
| Transport version | `1` |
| Meshtastic max `Data.payload` | `233` bytes |
| `SINGLE` control | `0x01` |
| `FRAGMENT` control | `0x41` |
| `SINGLE` header | `1` byte |
| `SINGLE` max envelope | `232` bytes |
| `FRAGMENT` header | `8` bytes |
| Message ID | `6` bytes |
| Fragment descriptor | `1` byte |
| Fragment body max | `225` bytes |
| Fragment count | `2..16` |
| Maximum fragmented envelope | `3600` bytes |

## 29. Summary

The Meshtastic transport carries the exact serialized `SignedEnvelope` to a configured gateway using reliable unicast.

Small envelopes use a one-byte framing header:

```text
01 | SignedEnvelope
```

Larger envelopes use bounded fragmentation:

```text
41 | message_id[6] | descriptor[1] | fragment_body
```

Meshtastic provides packet transport and routing acknowledgement. Connectivity Protocol remains responsible for authoritative sensor identity, signature verification, authorization, canonical deduplication, and upstream acceptance.
